# История обновлений BrickLab / Release history

История — публичный журнал развития, а не автоматический вывод git log. Обновляйте её в рамках каждого существенного пользовательского изменения, до объединения PR или выпуска. Один крупный PR может иметь несколько записей; мелкие коммиты объединяйте по смыслу.

## Добавление записи

В массив `releaseHistory` в `src/menu/home-hub.js` добавьте запись в начало (или на правильную позицию по дате):

```js
["YYYY-MM-DD","pull/123","Название RU","Что изменилось и зачем это пользователю.","English title","What changed and why it matters to builders."]
```

- Дата — реальная дата исходного коммита или объединения PR, не придуманная дата публикации. Если PR ещё не объединён, используйте дату исходного коммита и ссылку `commit/<SHA>` или номер уже открытого PR.
- Источник — реальный GitHub PR или SHA коммита с изменением. Не публикуйте секреты, личные данные или внутренние конфигурации.
- Заголовки уникальны в каждом языке; описание краткое, конкретное, на обоих языках. Отмечайте экспериментальные режимы, ограничения, тестовые платежи и статус подготовки. Не выдавайте код в ветке за уже развёрнутую функциональность.
- Сохраняйте старые записи и сортировку от новых к старым. Блок «Что нового» использует первую запись.
- Измените query-версию импорта `home-hub.js` в `src/menu/menu.js` и подключения `menu.js` в `index.html`, чтобы не оставлять старую историю в браузерном кеше.

## Проверка

```sh
node scripts/check-release-history.mjs
node --test tests/release-history.test.js
node scripts/check-release-history.mjs BASE HEAD
```

Последняя команда сравнивает два Git-коммита. Автоматический порог: пять изменённых файлов приложения, 200 добавленных/удалённых строк приложения, новый JS/TS-модуль в src/server или изменение миграции. Это консервативная эвристика, а не понимание семантики: крупная функция может занимать меньше строк, поэтому правило для разработчика действует и ниже порога. Проверка не способна оценить точность текста или подтвердить развёртывание; это часть ревью. Технические изменения, попавшие выше порога, требуют осмысленной записи о результате либо пересмотра порога в отдельном PR.

Структурный тест входит в `npm test`. GitHub Actions дополнительно сравнивает изменения PR в облачную ветку и прямые пуши в неё, если доступна исходная ревизия. Если обязательность проверки не настроена в branch protection, её красный статус сам по себе не блокирует merge. При ручном релизе сравните текущий развёрнутый SHA с целевым SHA до деплоя.
