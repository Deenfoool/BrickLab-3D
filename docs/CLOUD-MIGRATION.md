# BrickLab 3D — перенос на облачный сервер

Ветка: `feature/cloud-migration`. Базовая версия редактора сохраняется; GitHub Pages и `feature/mechanics-core` не изменяются.

## Этап 1 — HTTP и контейнер

Сервер Node.js 22 использует встроенный HTTP-модуль, не требует новых runtime-зависимостей. Он раздаёт редактор, каталог, модели, примеры и локальные библиотеки с одного origin. Разрешены только публичные каталоги и index.html; конфигурации, серверный код, скрытые файлы и обход каталогов запрещены. Gzip-пакеты передаются как исходные байты (без Content-Encoding), поскольку браузерный движок распаковывает их самостоятельно.

### Локальный запуск

```sh
npm start
curl -fsS http://localhost:8080/api/health
npm run test:server
```

Откройте http://localhost:8080/. Для запуска только на локальном интерфейсе: `HOST=127.0.0.1 npm start`. Сервер принимает HOST и PORT через переменные окружения.

### Docker Compose

```sh
cp .env.example .env
# Заполните BRICKLAB_DB_PASSWORD и BRICKLAB_APP_PASSWORD разными значениями в .env (openssl rand -hex 32)
docker compose up -d --build
docker compose ps
curl -fsS http://127.0.0.1:8080/api/health
docker compose logs -f bricklab
```

Контейнер работает от непривилегированного пользователя, с read-only файловой системой, healthcheck и graceful shutdown. По умолчанию порт опубликован только на loopback хоста. Для публичного доступа подключите reverse proxy с HTTPS к 127.0.0.1:8080; для управляемого контейнерного хостинга используйте Dockerfile и PORT провайдера. Не открывайте публичный HTTP-порт вместо TLS. Секреты не размещайте в src, assets, catalog или других публичных каталогах и не коммитьте .env.

### Важно для переезда

- Сборки пока остаются в localStorage браузера. Другой домен/порт — другой origin: старые проекты не появятся автоматически. Перед переездом экспортируйте важные сборки в .bricklab. Позже нужен импорт и проверяемая миграция в облако.
- HTTP API авторизации включается при настроенном PGPASSWORD; запись сборок и клиентские формы пока не реализованы.
- Внешние PDF и CDN пока работают как раньше. Сам сервер не устраняет CORS и не предоставляет произвольный прокси.
- Существующие тесты запускаются через npm test; HTTP smoke-тесты включены в общий набор. Docker-образ следует собрать и проверить на целевом хосте.

## Этап 2 — PostgreSQL и миграции

Docker Compose поднимает PostgreSQL 16 в закрытой сети, хранит данные в именованном томе `bricklab-db` и запускает отдельный одноразовый сервис `migrate`. HTTP-сервер стартует после успешного завершения миграций. У PostgreSQL нет опубликованного порта. Пароль администратора хранится только в окружении БД и мигратора, не передаётся веб-серверу.

Таблицы: `bricklab.users`, `bricklab.projects`, `bricklab.project_revisions`, `bricklab.project_members`, `bricklab.schema_migrations`. Идентификаторы UUID; модель хранится в JSONB без изменения формата `.bricklab` v1. Видимость по умолчанию приватная. Участники имеют роли editor/viewer, владелец хранится отдельно. Снимки ревизий запрещено изменять; указатель текущей ревизии проверяется внешним ключом. Создание проекта с первой ревизией и добавление следующей ревизии требуют транзакции. Авторизация и проверка прав на HTTP-уровне будут реализованы отдельно; наличие таблиц не означает готового контроля доступа. Миграция 002 создаёт отдельную непривилегированную роль приложения для авторизации.

Мигратор записывает SHA-256 каждой миграции, применяет новые SQL-файлы в порядке имени под advisory lock в одной транзакции. Повторный запуск пропускает применённые миграции, изменение применённого файла блокирует запуск. Не изменяйте существующие миграции — добавляйте новые (`002_...sql`).

```sh
docker compose up -d --build
docker compose logs migrate
docker compose run --rm migrate
docker compose exec -T db psql -U bricklab_admin -d bricklab -c 'TABLE bricklab.schema_migrations;'
docker compose exec -T db psql -U bricklab_admin -d bricklab < server/db/test-schema.sql
```

Не используйте `docker compose down -v` на работающем проекте: это удалит том БД. Перед обновлениями создавайте и проверяйте резервные копии. Изменение пароля в .env после первого запуска не изменяет пароль существующей роли автоматически; ротация выполняется отдельно.

## Этап 3 — серверная авторизация

Миграция 002 добавляет хеш пароля и таблицу сессий. Скрипт setup.sh применяет миграции и устанавливает пароль отдельной роли bricklab_app; роль не имеет прав на таблицы проектов или миграций. Веб-сервер не получает пароль администратора.

API: POST /api/auth/register (email, displayName, password), POST /api/auth/login (email, password), GET /api/auth/me, POST /api/auth/logout. JSON, точный Origin для POST, HttpOnly SameSite=Lax cookie (Secure и __Host- при HTTPS), случайный 256-битный токен, SHA-256 токена в БД, срок семь дней, scrypt для паролей (12–256 символов при регистрации), ограничение частоты и параллельности хеширования. Сессия при повторном входе заменяется. Регистрация по умолчанию выключена; для закрытого теста установите BRICKLAB_REGISTRATION_ENABLED=true. В production задайте PUBLIC_ORIGIN=https://ваш-домен без завершающего слеша. В режиме npm start без PGPASSWORD редактор работает без авторизации.

Ограничения: подтверждение email, восстановление пароля, MFA, распределённый rate limiter, интерфейс входа и права на модели ещё отсутствуют. За reverse proxy текущий IP-лимит общий для всех запросов с адреса proxy; перед публичным запуском настройте лимиты на доверенном прокси и распределённые ограничения. Не включайте открытую регистрацию до реализации этих мер. HTTPS обязателен вне localhost.

## Этап 4 — клиентский вход

На облачной ветке #account подключён к same-origin /api/auth. Пароли не сохраняются в localStorage, сессия — серверная HttpOnly cookie. Публичный HTTP блокируется клиентом, localhost разрешён для разработки. Регистрация по-прежнему отключена по умолчанию. Интерфейс честно сообщает, что облачное хранение и достижения ещё не подключены; демо-снимки и фиктивные роли не используются. Workshop из тестовой ветки будет перенесён после реализации серверного хранения. Проверки: `node --test tests/cloud-auth-client.test.js tests/server-auth.test.js`. На сервере требуется HTTPS перед публичным доступом.

## Этап 5 — приватные модели API

Миграция 003 добавляет RLS для роли приложения; контекст владельца устанавливается только на время транзакции из серверной сессии. GET/POST /api/projects; GET/PUT /api/projects/:id (PUT принимает document и expectedRevision); GET /api/projects/:id/revisions и /:revision. Несовпадение версии возвращает 409 revision_conflict. Неизменившийся документ не создаёт новую ревизию. Лимиты: 20 проектов, 20 ревизий на проект, тело запроса 2 МиБ, суммарный бюджет около 64 МиБ на аккаунт. Удаление, публикация, доступ участников и клиентская синхронизация пока отсутствуют. Перед обновлением создать резервную копию, выполнить docker compose run --rm migrate, затем пересобрать bricklab. Регистрация остаётся закрытой.

## Этап 6 — интерфейс облачных сборок

В личном кабинете доступны явное сохранение локальной сборки, список приватных моделей, скачивание и открытие актуальной или исторической версии как новой локальной копии. Локальная связь содержит ownerId, id, revision; редактор сохраняет её при локальном редактировании. PUT использует исходную ревизию, при 409 пользователь сохраняет локальные данные и может открыть свежую копию либо создать отдельный облачный проект. Никакой фоновой отправки или автоматического слияния нет. Локальные копии сохраняются после выхода, о чём интерфейс предупреждает. Проверки: tests/projects-client.test.js. Публичная регистрация остаётся выключенной.

## Этап 7 — перенос Workshop

Облачная ветка получает навигацию 14 разделов и рабочие страницы обзора, сборок, паспорта, хранилища и текущей идентичности/безопасности. Паспорт доступен для локальной модели и актуальной облачной ревизии; он проверяет структуру, не физику. Каталог достижений и испытания — без начисления XP, предварительная локальная оценка. Рейтинги, публичный профиль, дневник, бюро, избранное и уведомления обозначены как ещё не подключённые, без фиктивных данных. Проверка: tests/cloud-workshop.test.js.

## Этап 8 — профиль и серверные награды

Миграция 004 создаёт приватный профиль и журнал одноразовых наград. GET/PUT /api/profile возвращает собственный профиль и прогресс; PUT принимает только bio/cover. 30 XP за первое сохранение в облаке, одна запись на пользователя, начисление в транзакции создания проекта, существующим владельцам миграция начисляет тот же бонус. Это активность, не проверка инженерного навыка. Прочие награды не начисляются. Перед сборкой нового backend применить миграции к production и отдельно к browser test.

## Этап 9 — внешний вид и косметика

Миграция 005: приватные avatar/cover в PostgreSQL как ограниченные нормализованные WebP (до 512 КиБ каждый), RLS; хранение вместе с бэкапами и атомарная замена без файловых сирот. ImageMagick в контейнере, строгий список форматов, лимиты размеров и ресурсов, без SVG, метаданные удаляются. GET/PUT/DELETE /api/profile/avatar и /cover, только собственная сессия, no-store. Фоны отдельны от обложек: стандартный, за первую облачную сборку, две будущие платные темы (предварительные цены 99/149 RUB). Сервер проверяет владение при выборе. Таблица платных прав доступна приложению только на чтение; checkout отключён. Перед публичным запуском проверить декодер, политику обработки и платежную интеграцию.

## Этап 10 — активность

Дневник формируется из последних 100 реально сохранённых ревизий; неизменённое сохранение не создаёт события. Уведомления о подтверждённых наградах, отметки прочтения синхронизируются. Логический объём JSON всех ревизий отображается в хранилище. Публичные модели, подписки и социальные уведомления пока не подключены.

## Этап 11A — добровольные публичные карточки

Миграция 007 создаёт отдельные публичные снимки имени и описания. Приватные таблицы и фотографии не публикуются. GET/PUT/DELETE /api/community/me с сессией и проверкой Origin для записи; публичные GET /api/community и /api/community/profile/:id и HTML-страницы /community и /community/profile/:id. Каталог ограничен последними 30 карточками. Снятие публикации удаляет карточку. BRICKLAB_COMMUNITY_ENABLED=false по умолчанию; включать пока только в тестовой среде. ## Этап 11B — публикации сборок

Миграция 008 создаёт отдельные опубликованные снимки конкретных приватных ревизий. Публикация требует публичный профиль и явное согласие на скачивание полного файла; браузер передаёт только ID проекта, ревизию и описание. Сервер извлекает документ через RLS, новые приватные ревизии не обновляют публикацию. Снятие публичного профиля каскадно удаляет его публикации. GET /api/community/builds, /api/community/build/:id, HTML /community/build/:id и download; личное управление /api/community/me/builds. Ограничение каталога 30, без картинок, лайков, модерации, поиска или рейтингов. Community остаётся за feature flag.

## Этап 11C — галерея Community в основном меню

Миграция 009 добавляет категорию публикации и вычисляемое количество деталей. GET /api/community/builds поддерживает q/category/sort/offset/author, страницы по 24. Старые HTML-ссылки перенаправляются в основной интерфейс, загрузка файлов остаётся прежней. Поиск и сортировка выполняются на сервере. 3D-миниатюры генерируются существующим WebGL-рендерером из ограниченного геометрического представления, последовательно, до 8 автоматически на экран, максимум 600 деталей и 120 уникальных дизайнов; большая модель открывается отдельно по явному действию. Миниатюры не кэшируются постоянно. Открытие создаёт новую локальную копию, без связи с приватным проектом автора. Публичные аватары, интерактивное вращение, социальные функции и модерация отложены; Community выключен на основном сервере.

## Этап 11D — интерактивный просмотрщик

Кнопка 3D-просмотр на карточках и странице публикации открывает диалог без импорта в Мои сборки. Three.js OrbitControls, приближение, перемещение, сброс и полноэкранный режим; один просмотрщик на страницу, отрисовка по событиям, освобождение WebGL при закрытии/уходе. Используется ограниченное геометрическое представление previewDocument (600 деталей, 120 дизайнов); не воспроизводит физику, ремни, скрытые слои и кинематику, неизвестные детали пропускаются с указанием количества. Миграций нет.

## Этап 12A — публичное оформление

Миграция 010 добавляет отдельные снимки аватара, обложки (до 512 КиБ каждый), темы обложки и фона к публичным карточкам. Старые профили остаются без изображений. GET /api/community/profile/:id/avatar или /cover читает только опубликованные байты, no-store; метаданные содержат только публичные URL, без байтов и приватных ID. При явной повторной публикации копируется выбранное текущее приватное оформление; фон дополнительно проверяется по владению. Снятие галочки и сохранение либо снятие публикации удаляет публичный снимок; приватное редактирование само по себе публичный снимок не изменяет. Отдельные публичные изображения не загружаются, используются уже нормализованные WebP. Публичное сообщество по-прежнему только в тестовой среде.

## Этапы 12B/12C — реакции и подписки

Миграция 011: приватные RLS-таблицы лайков, подписок и уникальных событий (один аккаунт/сборка/тип за всё время), публичные агрегатные представления без идентификаторов пользователей. Авторские реакции и события не учитываются; гости читают и скачивают без учёта статистики. Лайки и подписки обратимы, лимит 1000 каждого на аккаунт. Просмотры при открытии страницы или успешном 3D-просмотре, скачивания при запросе файла; загрузка миниатюр и импорт используют /document и не увеличивают скачивания. Подписки не требуют публичного профиля. Лента доступна только владельцу сессии. Популярность: лайки, затем просмотры, затем время. Удаление публикации удаляет связанные записи. Счётчики не являются уникальными людьми и не защищают от мультиаккаунтов. Нет realtime, уведомлений и рейтинга репутации.

## Этапы 12D/12E — обсуждения и репутация

Миграция 012: комментарии под публичной сборкой, ответы одного уровня, до 1500 символов, 30 за сутки и 1000 всего на публичный профиль. Только владельцы публичного профиля пишут, гости читают. Удаление владельцем очищает текст, сохраняет ответы; снятие публикации удаляет обсуждение. Жалобы авторизованных пользователей (спам/оскорбления/другое) хранятся отдельно, одна на аккаунт и комментарий; пока только сбор жалоб, без автоматических санкций или админ-интерфейса. Рейтинг публичных авторов с хотя бы одной сборкой: 5 за полученный лайк, 3 за уникальное скачивание, 2 за подписчика. Динамически меняется при отмене реакций и снятии публикаций, не является квалификацией и не начисляет XP. Страница рейтинга по 30 авторов. Комментарии отображаются по времени, ответы отмечаются именем адресата. Community на основном сервере выключен.
