# BrickLab Control Center — phases 1–2 (read-only by default)
Same bot token as BrickLab Events, separate long-polling service. Existing notification worker and backup timers are not changed. No AI. The poller runs under a dedicated unprivileged systemd account, without Docker socket, repo or backup-directory access; the independent fixed root collector publishes only aggregate metrics. No raw logs, personal information or shell commands via Telegram.

## Before install
- Review and test this branch. No migration is required beyond existing 019 for event/bug statistics.
- Existing telegram.json must be root-owned, mode 0600, with a private positive chat_id. For a group destination, do not replace the existing config: the installer refuses it.
- Ensure no other getUpdates consumer or webhook uses the token. Existing sendMessage-only workers are compatible. A polling conflict is logged with code 409; do not delete webhooks automatically.
- Run python3 -B tests/telegram_control_test.py and bash -n scripts/install-bricklab-control.sh.
- From /opt/bricklab-cloud, after reviewed release is present: sudo bash scripts/install-bricklab-control.sh.
- Open the existing Telegram bot and send /menu, /status or /start.
- Check sudo systemctl status bricklab-control.service bricklab-control-snapshot.timer; sudo journalctl -u bricklab-control.service -n 30 --no-pager.
- Snapshot updates every 60 seconds after completion. Data older than 180 seconds is shown as unknown; HTTPS probe is from VPS, not external monitoring. Backup status reports systemd result only, not verified restorability.
- To disable: sudo systemctl disable --now bricklab-control.service bricklab-control-snapshot.timer bricklab-control-actions.socket bricklab-control-recovery.timer. Existing events continue.

## Optional operator actions
Default install disables the action socket. To explicitly enable after review and tests:
`sudo bash scripts/install-bricklab-control.sh --enable-actions`.
The Docker page can restart only an already running BrickLab app, not PostgreSQL. The backup page starts the two existing systemd backup services; successful units do not prove restorability. Buttons require private owner confirmation within 60 seconds; confirmation is single-use and lost on bot restart. The root broker independently checks the Unix peer UID, request shape and allowlist, serializes requests with the repository deploy script, and persists accepted requests and cooldowns in /var/lib/bricklab-control-actions/audit.sqlite3 (10 min restart / 30 min backup). The bot shows the last eight accepted operations in its audit page. View full journal with `sudo journalctl -u 'bricklab-control-actions@*'`. A timeout reports unknown, not success. A systemd job or Docker daemon operation may continue after its client times out; inspect it before manual maintenance. No automatic retries. A compromised bot account can invoke these two limited actions; Telegram confirmation is not a second authentication factor. Disable with `sudo systemctl disable --now bricklab-control-actions.socket`; in-flight operations may finish. Only the updated release script shares the lock; coordinate any manual deployment/maintenance separately. Logs show keyword counts only, not raw content. Run `python3 -B tests/telegram_control_actions_test.py` too.

## Phase 4: release overview
Shows checkout SHA, locally fetched remote-tracking SHA, behind count and tracked-file worktree status. Links to GitHub commits, Actions, pull requests and issues; issue creation is an authenticated GitHub web form or optional direct creation of a generic triage issue as described below. The GitHub page also reads the exact remote SHA and CI runs via the GitHub API on demand, cached for five minutes. Public repositories need no token. ## Phase 5: optional additional alerts
Off by default to avoid duplicating existing monitoring. Toggle in Automation, snooze additional alerts for one hour, or resume. Persistent state in the bot StateDirectory; two consecutive distinct snapshots are required for both alert and recovery; missing readings are unknown. Thresholds: local API and SQL failure, RAM >=90%, free disk <=10%, retrying events >=20. Sends one message per transition; quiet mode suppresses extra alerts only, not the original monitor or Events. A reboot keeps preferences; no changes to maintenance mode. An independent opt-in auto-recovery timer is described below. Existing daily digest remains the source of community daily statistics. Tests: python3 -B tests/telegram_control_automation_test.py.


### Optional recovery timer
Off on a fresh installation. Only after checking existing monitor recovery policies and testing the new service on a non-production instance, enable via `sudo systemctl enable --now bricklab-control-recovery.timer`. The root-owned collector must observe three distinct recent snapshots (running app, failed local API, SQL OK). Recovery takes the same lock as the release script, rechecks that the app is running, PostgreSQL is ready and API is still failing, and invokes only the existing fixed restart broker. Attempts at most hourly (manual restart cooldown also applies), persisted before execution; no retries, no startup of stopped services, no DB restarts. To pause before manual work: `sudo touch /etc/bricklab-backup/control-recovery.pause`; resume by removing the file. To disable: `sudo systemctl disable --now bricklab-control-recovery.timer`; an already running operation may finish. The quiet mode in Telegram is notification-only and does NOT pause recovery. Review recovery journal and shared action audit (Telegram and automatic recovery are distinguished). Run `python3 -B tests/telegram_control_recovery_test.py`. No independent external uptime monitor is provisioned here.


## Phase 6: analytics
Seven calendar days in database timezone, registration counts and current public builds grouped by their publication date (not historical publication event counts). Totals for likes, downloads/views recorded by community events, follows and parts. No invented online counts or editor telemetry.

## Phase 7: Mini App (read-only, opt-in)
After install, configure the existing HTTPS reverse proxy with a route for /control/ to http://127.0.0.1:8091/control/ (preserve path and X-Telegram-Init-Data; do not log this header). For nginx inside the existing site server block:
    location ^~ /control/ {
        proxy_pass http://127.0.0.1:8091;
        proxy_set_header Host $host;
        proxy_read_timeout 10s;
        access_log off;
    }
Review existing proxy CSP and frame headers so they do not block the Telegram web client. Do not expose port 8091 publicly. Start with sudo systemctl enable --now bricklab-control-miniapp.service. Verify an unauthenticated request to /control/api returns 403. Only after HTTPS route works, add Environment=BRICKLAB_MINIAPP_ENABLED=1 in a systemd drop-in for bricklab-control.service, daemon-reload and restart. The bot shows a private web_app button. The backend checks Telegram HMAC, owner ID and five-minute auth_date on every data request; reopen the Mini App when authorization expires. The dashboard snapshot endpoint only reads aggregates. Separate moderation UI uses existing site admin endpoints and site session; no bot token in browser. Disable by removing that Environment and stopping/disabling the miniapp service. Test with python3 -B tests/telegram_control_miniapp_test.py.


## Approved release from Telegram
After review and CI, root on VPS explicitly approves the exact locally fetched remote SHA: `sudo bash /usr/local/lib/bricklab-control/bricklab-control-approve.sh <40-hex-SHA>`. Approval expires in one hour and is consumed before release; it is not reusable. With action socket enabled, choose Version → approved release → confirm. The broker queues the fixed systemd service; queued does not mean deployed. The worker fetches the exact branch, refuses changed head and dirty tracked files, and invokes the installed release script, which runs isolated tests, production backups, migrations and health checks under the shared lock. Inspect service result in Version and journal via `sudo journalctl -u bricklab-control-release.service`. A failed release is not retried automatically. No Telegram-controlled rollback across schema changes. Review the installed runner whenever release gates change. Root approval is independent of Telegram; a compromised bot could trigger only an already approved SHA. Do not approve unreviewed commits.


## Restore verification
Root selects an existing root-owned local PostgreSQL custom-format dump (mode 0600); do not pass arbitrary URLs or unknown files. Run `sudo bash /usr/local/lib/bricklab-control/bricklab-control-verify-backup.sh /absolute/path/to/backup.dump`. The script acquires the shared release lock, creates a disposable isolated PostgreSQL 16 container (no host volume or networking), restores with pg_restore and checks two application tables, then removes the container and anonymous volumes. The result/time appears in Telegram. This does not validate configuration archives, application behavior or point-in-time recovery. Actual format/path of existing backups must be checked first.

## Independent monitoring
Copy only scripts/bricklab-control-external.py and scripts/install-bricklab-external.sh to a different trusted host. Provision root-only 0600 /etc/bricklab-external/telegram.json with token/chat_id (prefer dedicated alert bot); install via sudo bash install-bricklab-external.sh. Two failed HTTPS checks alert once, two successful checks notify recovery. It does not use getUpdates and may coexist with the operator bot. No second VPS was provisioned by this repository. For maintenance, existing recovery pause file prevents automatic restarts; it does not place the public website in maintenance mode.


## Public maintenance mode (optional nginx integration)
Review the existing reverse proxy first. Add the provided scripts/bricklab-control-maintenance.nginx.conf contents to every public application proxy location, including API routes, except /control/ (operator Mini App) and any explicitly retained health route. Keep payment callbacks accessible if live payments are enabled; do not enable maintenance without deciding callback routing. Use an internal nginx error_page 503 location serving the optional maintenance HTML if desired. Verify with nginx -t, reload, and manually exercise both states using the root-owned /run/bricklab-control-maintenance/enabled marker. Only after verification create root-only /etc/bricklab-backup/control-maintenance.enabled to expose the Telegram buttons. Do not leave maintenance active during the current deploy script's public health checks; use the separate recovery pause if needed. Maintenance stops automatic recovery, but independent uptime monitor may alert unless health route is exempt. The marker is intentionally volatile across reboot. Emergency reset: sudo rm -f /run/bricklab-control-maintenance/enabled. No unverified nginx edits are made by installer.

## Rollback policy
No arbitrary git reset or old image boot against a potentially incompatible database. For a code-only rollback, create a reviewed revert commit on the release branch, run the normal CI, approve its exact SHA and deploy as a new forward release. Database migration rollback requires a separate tested restoration procedure, a maintenance window, explicit data-loss assessment and operator authorization.

## Mini App moderation
The dashboard includes a separate moderation panel for accounts, reports and bug reports. It uses existing same-origin /api/admin endpoints, requiring an existing authenticated BrickLab administrator cookie as well as a fresh Telegram Mini App authorization in the UI. The server's original admin permission, origin, action validation and audit remain authoritative; Telegram never creates a site session or impersonates a site user. If the Telegram webview has no site session, sign in through the existing site and return to the panel if the client preserves cookies; otherwise use the normal web admin. The UI supports block/unblock, revoke sessions, hide comment, dismiss reports and unpublish builds with mandatory reason and short confirmation. Profile unpublishing remains in the full web admin. No raw log export or private project attachment upload. The loopback Mini App API itself remains read-only. Live client cookie behavior must be verified on mobile/desktop.


## Scheduled upkeep (Control OS phase 1)
Install separately after reviewing and testing: `sudo bash scripts/install-bricklab-upkeep.sh`, then rerun the Control Center installer (preserve existing actions policy). The existing bot and Mini App do not need a new Telegram token. Restart the active Mini App service to load the updated Python endpoint. The root sample service sends 75/85/90% disk alerts (recovery below 70%), samples app and Docker filesystems every five minutes and keeps 35 days of metrics. Reports run on the first successful sample after Monday 09:00 MSK, only when the prior period has samples; availability is successful sampled HTTPS requests from the VPS, not external uptime. Missing samples are not successes. Delivery may retry on a subsequent sample if Telegram is unavailable. Existing optional critical disk alert remains separate.

The daily 04:00 MSK cleanup timer defaults to preview. Inspect `sudo python3 /usr/local/lib/bricklab-control/bricklab-control-upkeep.py preview` before enabling actual cleanup with `sudo touch /etc/bricklab-backup/upkeep-cleanup.enabled`. Remove that marker to return to preview. No global image prune, no volume/container deletion, no force. Only default dangling builder cache older than 168h and old exact BrickLab rollback tags are eligible; current and stopped-container images, test images and all unrelated tags are preserved. Three newest rollback tags are retained, plus tied/used images. New release runner records successful release time; legacy tags sort by image creation time. Shared release lock prevents overlap with supported deployments and restores. Free-space delta is measured, not attributed exclusively to Docker. Manual unrelated operations must coordinate with the same lock. Mini App shows aggregate status only, no root commands. Run `python3 -B tests/telegram_control_upkeep_test.py` and `bash -n scripts/install-bricklab-upkeep.sh`. 

Control OS tabs: Home, People (existing site admin session required), Finance (live aggregate SQL, excludes test orders), Dev (existing release diagnostics), VPS. Dev remains read-only in Mini App; deployment approval policy is unchanged. Existing Commerce Telegram worker handles payment/refund/receipt notifications when configured; no duplicate notification sender is added. No automatic financial mutations.

Root-only test mode: `bash /usr/local/lib/bricklab-control/deploy-community-vps.sh <exact-sha> --test-only <remote-branch>`. Fetches that branch and checks its exact SHA, rejects symlinks/submodules, runs the existing isolated tests under the shared lock and exits before backups, checkout changes or production deployment. It does not expose a branch selector or a root command endpoint to Mini App. Tests for older branches lacking required files fail safely. Production still requires the existing reviewed fast-forward release gate.

## Control OS jobs (optional)
Install `bash scripts/install-bricklab-jobs.sh` after the updated control installer; the socket allows branch listing and job status. Root enables submissions with `touch /etc/bricklab-backup/control-jobs.enabled`. Mini App verifies fresh owner initData and same-origin POST; the separate Unix broker verifies the dedicated UID, request schema and idempotency. Jobs are serialized by a fixed systemd worker and the existing deploy lock. The test job runs the installed runner against the exact current remote branch SHA; no arbitrary commands or URLs. The most recent job status and fixed stages are visible, with numeric TAP failure count where available; raw output stays root-only at /var/lib/bricklab-control-jobs/last.log (max 8 MiB). Telegram receives final status. Deploy requires a successful test of that same production branch SHA and the existing independently approved SHA; the release runner independently rechecks it and runs the full suite again. Unmerged branches can be tested but not deployed directly. Disable new submissions by removing the marker; stopping the socket does not cancel an in-progress job. No automatic retry of interrupted deployment. The existing bot release controls remain separate. Use only repository branches trusted to execute code in the isolated test environment; containers are not a security sandbox against malicious contributors. Test mode does not imply review or authorize deployment.


## BrickLab Hub (user-facing, opt-in)
The same polling bot serves the private operator menu and the user-facing /hub menu. Ordinary private chats receive only the Hub button when enabled. The existing root-owned Telegram chat ID remains the sole Control OS owner. The Hub is separately served at /control/hub/ and uses verified Telegram initData; the Node application receives a short-lived HMAC-signed bridge request over loopback, not the bot token. The website session creates a random 192-bit pairing code, stored hashed for ten minutes; the code is redeemed once, with uniqueness in both directions. Unlink on the website. Blocked/unverified accounts cannot link or resolve their identity. Marketing is off by default.

After reviewing and running the full isolated release checks, install the new application and migration 114–116 using the standard release process. Provision the bridge key with `bash scripts/install-bricklab-hub.sh` (before rebuilding the application so compose reads the key-file setting). The existing private commerce directory must be traversable by the container's node user; key mode 0440 root:1000, no secret value in the environment. The installer copies a second root-only key into systemd credentials and derives the owner ID from existing root config. Verify the app can read its mounted key, the Hub is healthy and the admin account is linked. Install the updated Control Center scripts and restart bot/Mini App. /control/api and /control/jobs remain owner-only; /control/hub/api requires valid initData and returns only the linked account. Promos and campaigns also require the linked site's admin role.

Plus-day promos are distinct free entitlements, never artificial payments. Once per user, capped globally and by expiry, serialized by the commerce user lock. Paid renewal is scheduled after any existing promo period. Only Plus days are implemented; checkout discounts and other promo reward types are not yet integrated. Marketing campaigns support text, draft, owner test send, scheduled confirmation, cancellation and aggregate delivery counts. Consent is checked again at claim; messages already in flight cannot be recalled. Ambiguous Telegram sends become unknown instead of being retried; explicit 429 retries with delay. Enable the separate worker only after tests: `systemctl enable --now bricklab-hub-campaign.timer`. It uses sendMessage only, not getUpdates. All opted-in linked accounts form the current supported audience. The Hub shows delivered campaign history and the existing public rankings. Personal social/expiry push notifications are not yet implemented. Test migration and authorization in a disposable database before production.
